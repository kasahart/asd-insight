# 大規模WAVの検証（Issue #9）

2026-09-29。10万WAVは検証基準であり、仕様上の件数上限ではない。旧WAV 2,000件、CSV 100,000行の固定制限を取込・評価・保存・保存状態の検証から撤去した。100,001件でも確認する。

## 変更

- `Dataset.rows` は元CSV行を共有する。階層属性は `derivedColumns: Map<列名, Map<行index, 文字列>>` に非空セルだけを保持し、未対応・曖昧・階層欠測は空文字として参照する。
- `datasetRows(dataset)` はキャッシュした読み取り専用ビューを返す。群分け、フィルタ、一覧、ソート、詳細の列挙、CSV出力、来歴署名はこの境界を使う。ビューをstructured cloneしない。Dataset本体だけを転送する。
- 元行の文字列own property契約は維持し、ワーカーは派生列の型・行index・元列との衝突も検証する。同じ元行配列の階層更新では、登録キーに結びついた差分だけを送る。キャンセル・タイムアウト・失敗時は登録を破棄して再送する。
- 保存は従来どおり元CSV＋WAV対応＋解析状態。派生列は再構築するため、保存形式・バックアップ版番号は変更しない。
- バックアップ復元は音声ごとの `Blob.slice` を、一度のpayloadストリーム読みに変更した。多数のBlob断片からなるバックアップの繰り返し走査を避け、各資産のhash検証と容量検証は維持した。
- 保存時の元列検証をSet参照にし、行ごとの列名照合が列数の二乗にならないようにした。

## 計測方法

```sh
node --expose-gc scripts/benchmark-scale.mjs
node scripts/benchmark-storage-scale.mjs 100001
npm run e2e -- tests/e2e/scale.spec.ts
```

Node 24.15.0、Linux、Intel Core i7-13700KF、RAM約126GiB。単発の開発機計測であり、端末間の保証値や信頼区間ではない。生結果は [評価計測](benchmarks/issue-9-scale.json)、[保存計測](benchmarks/issue-9-storage.json)、[stream化前](benchmarks/issue-9-storage-before-stream.json)。

評価計測は1,000 / 10,000 / 100,000行×128列、同数のWAV対応、2階層。音声パスとスコア以外の126列は空文字。比較対象は改修前と同じ全行spreadコピーを行う実装をハーネス内に残したもの。各条件は独立プロセスで実行し、元行を保持したまま測定する。実Node Workerで群分け、フィルタ、パスソートと件数保存則を確認する。WAVはメタデータ照合用の合成Fileで、音声デコードは行わない。

heapはGC前の差分、強制GC後の差分を測る。保持量にはUI用行ビューを含む。同期処理中の正確なheapピークは観測できないので、GC前値をピークと呼ばない。プロセス全体のピークRSS（OS high-water mark）も記録する。転送量はV8 serializeで測るペイロード相当量であり、ブラウザーの内部wire byte数ではない。実Worker往復時間には起動・structured clone・評価・結果返却・計測用GCも含む。

| 行数 / WAV数 | 表現 | 属性生成 ms | GC前追加heap MiB | GC後保持 MiB | 初回転送相当 MiB | 階層更新転送相当 MiB | Worker往復 ms | ピークRSS MiB |
|---:|---|---:|---:|---:|---:|---:|---:|---:|
| 1,000 | 行コピー | 0.7 | 1.6 | 1.0 | 1.0 | 0.95 | 71.7 | 125.9 |
| 1,000 | 疎な列 | 0.6 | 0.7 | 0.1 | 0.9 | 0.02 | 73.0 | 124.2 |
| 10,000 | 行コピー | 4.5 | 15.8 | 10.6 | 9.5 | 9.53 | 170.4 | 223.2 |
| 10,000 | 疎な列 | 4.1 | 6.9 | 1.8 | 9.2 | 0.17 | 169.6 | 206.7 |
| 100,000 | 行コピー | 70.8 | 109.8 | 106.1 | 95.5 | 95.52 | 1,290.8 | 901.3 |
| 100,000 | 疎な列 | 46.3 | 56.0 | 16.2 | 91.9 | 1.80 | 1,330.0 | 816.7 |

10万件では追加保持量約85%減、階層更新時の転送量約98%減。初回転送は元CSVが占めるため約4%減にとどまる。WorkerのGC後保持量は約151→165MiBと増える（受信側は元行・派生Map・ビューを持つ）。評価速度の改善は主張しない。主な改善は元CSVと派生行の二重保持・反復転送の削減。

## 保存と復元

100,001行×3列、100,001個の異なる48-byte有効PCM WAV、2階層、バックアップ約36.6MiBで検証。IndexedDB/OPFSは既存のテストアダプターを使うため、以下は実ディスク性能ではない。

| 処理 | 時間 |
|---|---:|
| 新規保存 | 3.98秒 |
| Repositoryを閉じて再読込 | 2.14秒 |
| バックアップ出力 | 2.63秒 |
| 別Repositoryへの復元 | 6.21秒 |

stream化前の復元45.16秒から約86%短縮。元CSVの一致、音声件数、全行の照合成功、再構築後の階層署名一致をassertする。ハーネスは元データ・読込後データ・バックアップ・復元先を同時保持し、全工程のピークRSSは約1.48GiB。最小メモリ要件を示すものではない。

## 実ブラウザーと回帰検証

実Chromiumで100,001行×3列・100,001個のFileを取り込み、階層による群分け、末尾ファイルの検索、端末保存、ページreload後の再読込と検索／群分けの復元を確認した。FileSystemDirectoryHandleは合成し、ブラウザー側のCSVワーカー・評価ワーカー・IndexedDB・OPFSは実装を使った。音声内容は同一の48-byte PCMなので、保存時は既存仕様に従い内容で重複排除される。100,001個の異なる内容は上記保存アダプター試験で別途確認した。

取込開始から群分け・検索・保存完了まで52.8秒、reloadと再読込を含むE2E全体は約1.6分。操作の即時完了や実フォルダ走査速度は保証しない。実ブラウザーの未処理例外なし。

最終確認: `npm test` 304件成功、E2E 26件成功（既存25件＋100,001件試験）、build・typecheck・lint成功。ルートの旧ドメインテストは `evaluation-reference.test.mjs` の互換ハーネス経由で実行する既存構成を維持した。

## 検証の範囲と残る容量条件

10万件すべてをデコード・再生した試験ではない。通常のUIと同じく、音声の対応・属性・評価・保存を対象とする。長時間音声の総容量、ストレージ速度、端末RAMによる制約は別に残る。

既存のCSV 20MiB・128列、階層64、単一音声80MiB、展開後dataset metadata 48MiB、バックアップ128MiB、保存合計256MiB（配信設定による縮小あり）は維持している。固定件数制限を撤去しても、これらの容量条件を超える入力が保存できるわけではない。特に**10万行×128列の評価計測は、同じ幅のCSV＋10万音源を丸ごと保存できる保証ではない**。列名を各行に持つ既存保存形式ではmetadata容量が先に効く。大容量の実音源を10万件丸ごと保存するには、外部ファイル参照・ストリーミング保存／バックアップ等を含む保存設計の拡張が別途必要になる。

回帰テストは元行不変、欠測・曖昧照合、特殊列名、列挙／CSV出力、評価同値性、階層署名、実Worker差分登録／再起動、壊れた派生列の拒否、空・複数chunkに跨る資産の復元を含む。
